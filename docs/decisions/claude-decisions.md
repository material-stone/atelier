# Claude 판단 기록

Claude가 구현하면서 정한 설계와 그 이유입니다. 사용자가 정한 방향은 [user-decisions.md](user-decisions.md)에 있습니다.

## 2026-11-10 · 업로드 API — 게임 정보 반영 시점, 전역 CLI·스킬

### 바꾼 게임 정보는 별도 컬렉션에 보관했다가 공개 순간에 반영

- **결정:** 공개 중인 게임을 업데이트하면 바꾼 정보(제목, 설명, 장르, 접근 등급, 초대 이메일)를 `pendingGameUpdates/{versionId}`에 둔다. `processBuildZip`이 빌드를 공개할 때 같은 `update`로 함께 반영하고, 실패·취소·다른 업로드로 대체되면 버린다. 이로써 "중단 처리"에서 남은 한계로 적었던 항목을 해결했다(사용자 지적).
- **이유:** `games/{id}` 문서는 공개로 읽히므로 초대 이메일을 그 안에 둘 수 없다. 버전별 문서로 두면 같은 게임에 업로드가 겹쳐도 어느 정보가 어느 빌드와 짝인지 헷갈리지 않는다. 규칙에 이 컬렉션을 넣지 않아서 클라이언트는 읽거나 쓸 수 없다.
- **순서:** 비공개로 바뀔 때는 초대 목록을 먼저 쓰고, 비공개에서 벗어날 때는 게임 문서를 바꾼 뒤 지운다. 기존에 정보를 직접 수정할 때와 같은 순서다.
- **범위:** 웹 업로드 룸도 같은 `prepareGameDraft`를 쓰므로 똑같이 바뀐다. 업로드가 끝나기 전에 정보가 먼저 바뀌는 문제는 웹에도 똑같이 있었기 때문에 따로 남겨 두지 않았다. 아직 공개되지 않은 게임(처리 중, 실패)은 누구에게도 보이지 않으므로 지금처럼 바로 반영한다.
- **알아둘 점:** 업데이트가 처리되는 동안 관리자 화면에서 정보를 직접 고치면, 빌드가 공개될 때 보관해 둔 값으로 덮어써진다.

### 전역 CLI는 `npm link`, 설정은 사용자 홈 폴더의 파일 하나

- **결정:** `tools/atelier-upload/package.json`의 `bin`으로 `atelier-upload` 명령을 만들고 `npm link`로 전역 설치한다. 키와 URL은 `atelier-upload --init`으로 `~/.atelier-upload/config`에 저장한다. 읽는 순서는 환경변수 > 사용자 설정 > 도구 폴더 `.env`다.
- **이유:** 링크라서 Atelier 저장소를 pull하면 모든 프로젝트에서 바로 새 버전을 쓴다. 키가 PC에 한 곳에만 있어서, 바꿀 때도 한 곳만 고치면 된다. 프로젝트마다 `.env`를 복사하면 키가 여기저기 흩어진다.
- **주의:** worktree에서 `npm link`를 하면 worktree가 지워질 때 링크가 깨진다. 그래서 원본 체크아웃에서 설치하도록 문서에 적었다. 검증할 때는 worktree에서 잠깐 링크했다가 해제했다.
- **`--config`:** 키를 가린 채 어디서 읽었는지 보여 준다. Claude가 키 원문을 보지 않고도 준비됐는지 확인할 수 있다.

### 스킬은 CLI를 감싸는 사용 설명서로 한정

- **결정:** 전역 스킬 `atelier-upload`에는 업로드 로직 없이 절차만 담는다: 준비 확인, ZIP 만들기, 새 게임과 업데이트 구분, 실패했을 때 대처. 원본은 저장소의 `tools/atelier-upload/skill/SKILL.md`에 두고 `~/.claude/skills/`에 복사한다.
- **이유:** 업로드 로직이 스킬에 있으면 Claude가 매번 코드를 다시 쓰게 되어 불안정하다. 원본을 저장소에 두면 변경 이력이 남는다. Windows에서 심볼릭 링크는 관리자 권한이나 개발자 모드가 필요해서 복사로 했다.
- **키 취급:** 스킬은 키를 대화로 받거나 명령줄 인자로 넘기지 말고, `--init`은 사용자가 직접 실행하게 한다. 키는 관리자 권한과 같아서 대화 기록이나 셸 기록에 남지 않게 했다.
- **ZIP 만들기:** 앞에서 "폴더를 ZIP으로 묶는 기능은 CLI에 넣지 않는다"고 정한 대신, 스킬에서 Windows 내장 `tar.exe -a`로 묶도록 했다. Git Bash의 `tar`는 GNU tar라서 ZIP을 만들지 못하므로 경로를 지정해 부른다. 이렇게 만든 ZIP은 항목이 `./`로 시작하지만 서버의 `safeArchivePath`가 이를 제거하는 것을 확인했다.

## 2026-11-10 · 업로드 API — 중단 처리

### Ctrl+C는 취소, 연결 실패는 이어 올리기

- **결정:** 사용자가 Ctrl+C를 누르면 업로드 세션을 끊고 서버 초안을 되돌린다. 재시도까지 실패했거나 프로세스가 죽은 경우에는 진행 상태를 남겨 두고, 같은 명령을 다시 실행하면 이어서 올린다. `--cancel`로 명시적으로 되돌릴 수 있다.
- **이유:** Ctrl+C는 "그만두겠다"는 뜻이 분명하니 흔적을 남기지 않는 게 맞다. 연결 실패는 사용자가 원한 중단이 아니라서, 250MiB를 처음부터 다시 올리게 하는 것보다 이어 올리는 게 낫다.
- **대안:** Ctrl+C도 이어 올리기용으로 남기는 방법이 있었지만, 그러면 '처리 중'으로 남은 게임을 사용자가 직접 치워야 해서 이번 작업의 목적과 맞지 않는다.

### 서버 취소는 "아직 처리 대기 중인 이번 버전"에만 작동한다

- **결정:** `DELETE /games/{id}/versions/{versionId}`는 그 버전이 아직 대기 중일 때만 되돌린다. 게임 문서는 이번 업로드로 처음 만들어졌을 때만 지운다. 이를 판단하려고 새 게임에 `createdByVersionId`를 기록하고, 공개되면 지운다.
- **이유:** 늦게 도착한 취소 요청이 이미 공개된 빌드나 그 사이 올라온 다른 업로드, 예전부터 있던 게임을 지우면 안 된다.
- **추가 안전장치:** CLI는 취소하기 전에 ZIP이 Storage에 다 올라갔는지 확인한다. 다 올라갔으면 이미 처리가 시작됐으므로 취소하지 않는다.

### 업데이트는 ZIP을 먼저, 표지를 나중에

- **결정:** 새 게임은 표지 → ZIP, 업데이트는 ZIP → 표지 순서로 올린다.
- **이유:** 업데이트 중에 멈추면 표지만 새것으로 바뀐 채 빌드는 예전 것인 상태가 생긴다. 표지는 같은 경로를 덮어쓰기 때문에 되돌릴 방법이 없다. 새 게임은 ZIP이 처리되는 순간 공개되므로 표지가 먼저 있어야 한다.
- **남은 한계:** 업데이트 때 함께 바꾼 제목·설명은 초안을 만들 때 바로 반영돼, 취소해도 되돌리지 않는다. 이전 값을 보관했다가 복원할 만큼의 문제는 아니라고 판단했다.

### 진행 상태는 사용자 홈 폴더에 저장

- **결정:** `~/.atelier-upload/state/<해시>.json`. 해시는 API URL, 요청 내용, 파일 경로·크기·수정 시각으로 만든다. 6일이 지나면 버린다.
- **이유:** 저장소 안에 두면 git에 섞일 수 있고, 나중에 CLI를 전역으로 쓰게 돼도 위치가 바뀌지 않는다. 파일이 바뀌었는데 이어 올리면 망가진 ZIP이 되므로, 수정 시각까지 포함해 같은 파일일 때만 이어 올린다. 업로드 세션 유효기간(7일)보다 조금 짧게 잡았다.

## 2026-11-10 · 업로드 API

### 파일은 함수를 거치지 않고 Cloud Storage로 직접 보낸다

- **결정:** API는 게임 문서만 갱신하고 Cloud Storage resumable upload 세션 URL을 돌려준다. CLI가 그 URL로 파일을 직접 PUT한다.
- **이유:** Cloud Functions 요청 본문은 32MB까지라 250MiB ZIP을 받을 수 없다. 함수를 통과한 바이트는 전송 요금도 붙는다. 웹 업로드도 이미 Storage로 직접 올리는 구조라 그대로 따랐다.
- **대안:** 서명 URL(v4 PUT)도 가능했지만 한 번에 올려야 해서 끊기면 처음부터 다시 해야 한다. resumable 세션은 8MiB씩 올리다 끊겨도 이어서 올릴 수 있고, URL 서명 권한도 필요 없다.

### 검사·압축 해제는 기존 processBuildZip을 그대로 쓴다

- **결정:** API로 올린 ZIP도 `incoming-builds/upload-api/{gameId}/{versionId}.zip`에 떨어져 같은 트리거가 처리한다. 초안을 만드는 코드는 `prepareGameDraft`로 빼서 웹 callable과 API가 함께 쓴다.
- **이유:** 경로 순회·용량·파일 수 검사, 이전 빌드 유지, 실패 시 롤백 같은 규칙을 두 군데서 따로 관리하면 언젠가 어긋난다.

### 인증은 Secret Manager에 둔 API 키 하나

- **결정:** `UPLOAD_API_KEY` 시크릿과 `Authorization: Bearer` 헤더로 인증한다. 키는 관리자 권한으로 취급한다.
- **이유:** 관리자가 한 명이고 목적이 자동화라서, Google 로그인 토큰을 갱신하거나 서비스 계정 JSON을 다루는 것보다 단순하다. App Check는 브라우저용이라 이 함수에는 걸지 않았다.
- **대안:** 로컬에서 `firebase-admin`과 gcloud 자격증명으로 직접 올리는 스크립트도 가능했지만, gcloud 로그인이 필요한 기기에서만 쓸 수 있고 요청한 "API"가 아니다.

### 기존 게임 업데이트 때 생략한 항목은 지금 값을 유지한다

- **결정:** `gameId`나 같은 제목으로 기존 게임을 지정하면, 요청에 없는 제목·설명·장르·접근 등급·초대 이메일은 기존 값을 채워 넣는다. 제목을 바꿀 때는 다른 게임과 겹치는지 확인한다.
- **이유:** 웹 업로드 룸은 폼 내용으로 메타데이터를 덮어써서, 빌드만 바꾸려다 설명이 지워지는 일이 있었다. 자동화에서는 "빌드만 교체"가 가장 흔한 작업이다.
- **결과:** 웹 업로드 룸의 덮어쓰기 동작은 바꾸지 않았다(요청 범위 밖).

### CLI는 의존성 없는 Node 스크립트

- **결정:** `tools/atelier-upload/upload.mjs`는 Node 18+ 내장 `fetch`만 쓴다. 설정은 환경변수나 같은 폴더의 `.env`(git 제외)에서 읽는다.
- **이유:** `npm install` 없이 어느 기기에서든, Claude가 Bash로 바로 실행할 수 있게.
- **안 한 것:** 폴더를 받아 ZIP으로 묶는 기능은 넣지 않았다. Node 내장 기능으로는 ZIP을 만들 수 없어 의존성이 생기고, Windows `Compress-Archive`는 버전에 따라 경로 구분자가 `\`로 들어가 서버 검사에 걸릴 수 있다.

### 새 게임은 표지 필수, 업데이트는 선택

- **결정:** 웹 업로드 룸과 같은 규칙. 업데이트에서 표지를 생략하면 기존 표지를 유지한다.
- **이유:** 홈 화면 카드에 표지가 없으면 깨져 보인다.

### 처리 완료까지 기다린다 (기본값)

- **결정:** CLI는 업로드 후 5초마다 상태를 확인해 공개·실패를 알려 준다. 최대 12분(`processBuildZip` 제한 9분 + 여유). `--no-wait`로 끌 수 있다.
- **이유:** 자동화에서는 "올렸다"보다 "공개됐다/실패했다(이유)"가 필요하다.
