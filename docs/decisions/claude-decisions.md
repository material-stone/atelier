## 2026-11-11 · YouTube 구독 확인의 "확인되지 않은 앱" 경고

### 원인과 해결 경로: Google OAuth 검증

- **원인:** `youtube.readonly`는 Google의 민감한 범위라, 검증 전에는 테스트 사용자가 아닌 모든 계정에 경고가 뜬다. 코드로 없앨 방법은 없다.
- **결정:** 검증 신청에 필요한 것을 준비했다. 개인정보처리방침에 Google API 사용자 데이터 정책(Limited Use) 준수, YouTube 약관·Google 개인정보처리방침 링크, 권한 해제 방법을 추가했다. 신청 절차, 영문 범위 사용 사유, 데모 영상 구성을 `docs/oauth-verification.md`에 정리했다. 신청 자체는 Cloud 프로젝트 소유자가 Console에서 해야 한다.
- **같이 바꾼 것:** `subscriptions.list`를 `part=snippet` 대신 `part=id`로 호출한다. 구독 여부만 필요하므로 받는 데이터를 줄이면 범위 사용 사유와도 맞는다.
- **대안:** 구독 확인을 없애고 수동 확인으로 바꾸는 방법은 운영 부담이 커서 쓰지 않았다. 구독 여부를 확인할 수 있는 더 좁은 범위는 없다.

### /about·/privacy를 200으로 응답

- **문제:** GitHub Pages는 SPA 딥링크를 `404.html`로 처리해 화면은 열리지만 HTTP 상태가 404다. 검토자는 홈페이지·개인정보처리방침 주소가 정상으로 열리는지 확인하므로 거절될 수 있다.
- **결정:** `scripts/copy-spa-fallback.mjs`가 빌드 결과의 `index.html`을 `about/index.html`, `privacy/index.html`에도 복사한다. Console에는 끝에 `/`를 붙인 주소(`/about/`, `/privacy/`)를 넣는다.
- **대안:** 모든 경로를 정적 파일로 만드는 사전 렌더링은 검증에 필요한 두 페이지에 비해 과하다.
- **도메인:** 승인된 도메인을 소유를 증명할 수 없는 `github.io`에서 `materialstone.dev`로 바꾸고, Search Console에서 Cloudflare 자동 TXT 레코드로 소유를 확인했다.

## 2026-11-11 · 단계 태그와 접근 등급 분리

### 접근 등급 값은 그대로 두고 `stage` 필드만 더한다

- **결정:** `stage`(`release` · `demo` · `prototype`)를 새로 두고, `accessLevel`은 `public` · `member` · `private`로 남긴다. 프로토타입은 `member`, 로테이션은 `member` 게임에서 고른다.
- **이유:** rules·Functions·CLI가 `accessLevel` 문자열을 쓰는 곳이 많아, 값의 이름을 바꾸면 고칠 곳과 마이그레이션 위험이 커진다.
- **`subscriber` 등급:** 처음에는 사용자 결정에 없던 등급이라 선택지로 남겼다. 사용자가 쓰지 않겠다고 해서 `login`처럼 없앴다. 저장된 `subscriber`는 `member`로 읽는다. 마이그레이션 전까지 서버의 로테이션 후보 쿼리에도 넣어, 브라우저와 서버가 같은 후보를 쓰게 했다.

### 예전 `login`·`subscriber` 값은 읽을 때 새 값으로 바꾼다

- **결정:** 클라이언트·서버 모두 `login`은 `public` + `demo`로, `subscriber`는 `member` + `prototype`으로 읽는다. 옛 CLI가 이 값을 보내도 받아 준다(새 CLI는 안내 메시지와 함께 거부). rules의 목록 허용 값과 게임 목록 쿼리에는 두 값을 마이그레이션 전까지 남겼다. 모르는 값은 `private`으로 읽어 막는다.
- **이유:** 배포와 `migrate-stages` 실행 사이에 남은 게임이 목록에서 사라지거나 잠기지 않게 한다.

### 마이그레이션 스크립트 `migrate-stages`

- **결정:** `public`→`release/public`, `login`→`demo/public`, `subscriber`·`member`→`prototype/member`, `private`→`prototype/private`. 이미 `stage`가 있으면 유지한다. `pendingGameUpdates`의 보류된 메타도 같이 바꾼다. 기본은 미리보기, `--apply`로 쓴다. `updatedAt`은 건드리지 않는다.
- **이유:** 보류된 업데이트가 나중에 공개되면서 옛 등급을 되돌려 놓는 일을 막는다. `updatedAt`을 바꾸면 홈 목록 순서가 뒤섞인다.
- **비공개 게임 기본 단계:** 초대 게임은 대개 시험 빌드라 `prototype`으로 했다. 관리 화면에서 바꿀 수 있다.

### 로테이션: 기준 주부터 한 주씩 이어서 계산

- **결정:** 개수는 `max(1, round(30%))`. 2026-11-09(KST 월요일) 주부터 시작해 매주 "지난주에 안 고른 게임"을 먼저 섞어 뽑고, 모자라면 지난주 게임으로 채운다. 저장 없이 주차 시드로 계산한다.
- **이유:** "지난주 제외"를 저장소 없이 지키려면 지난주 결과를 같은 규칙으로 다시 계산해야 하고, 그러려면 고정된 시작점이 필요하다. 한 해에 52번 반복이라 비용은 무시할 만하다. 클라이언트와 서버가 같은 결과를 내는지 테스트로 확인한다.
- **한계:** 게임이 추가·삭제되면 그 주의 선택이 바뀔 수 있다(기존 로테이션도 마찬가지였다).
- **대안:** Firestore에 주마다 결과를 저장하는 방법은 스케줄 함수와 쓰기 권한이 더 필요해서 쓰지 않았다.

### 권한: 로테이션은 로그인한 구독자에게만

- **결정:** 예전에는 로테이션 게임이 비로그인 사용자에게도 열렸지만, 이제는 구독 확인이 필요하다.

### 표시

- 단계 태그(공개·데모·프로토타입)는 색 없는 태그로, 접근 태그는 `public`이 아닐 때만 보인다. 목록 배지는 "이번 주 구독자" → 단계 → 접근 등급 순서로 하나만 보인다.
- 관리 화면에서 단계를 바꾸면 공개 범위가 그 단계의 기본값(공개·데모→누구나, 프로토타입→멤버)으로 바뀐다. 초대 게임은 그대로 둔다.

### 이번에 하지 않은 것

- `video/`(소개 영상)의 등급 표시는 따로 만든 프로젝트라 그대로 두었다. 다음에 영상을 다시 만들 때 맞춘다.

## 2026-11-10 · 세이브 브리지 불러오기 실패 처리

### 피드백 확인 결과: 맞다

- `load()`가 `store.load` 실패를 `.catch(() => (items = {}))`로 삼켜 빈 사본을 만들고 있었다. 그 뒤의 `storage-set`은 빈 사본을 기준으로 저장소에 그대로 써서 같은 키의 진짜 세이브를 덮어쓴다.

### 실패한 불러오기는 잊고, 다음 메시지마다 다시 시도

- **결정:** 실패한 Promise는 `loading`에서 지운다. hello뿐 아니라 set·remove도 먼저 불러오기를 시도하고, 실패하면 `load-failed`로 답하고 쓰지 않는다.
- **이유:** set이 다시 시도해서 성공하면 진짜 사본 위에서 쓰는 것이라 안전하다. 실패하면 쓰지 않는다. 그래서 "불러오지 못한 동안"을 따로 상태로 들고 있을 필요가 없다.

### 게임 쪽 예시: 다시 묻고, 끝내 실패하면 거부하며 localStorage로 넘어가지 않는다

- **결정:** `createAtelierStorage()`가 `load-failed`를 받으면 0.5초 간격으로 세 번까지 hello를 다시 보낸다. 그래도 실패하면 Promise를 거부한다. 플레이어가 어떤 `atelier:storage-*` 답이든 보내면 1.5초 대체 타이머를 끈다.
- **이유:** 피드백에는 없던 문제다. 기존 예시는 ready가 안 오면 1.5초 뒤 iframe `localStorage`로 넘어갔다. 그러면 불러오기 실패가 결국 빈 세이브가 되고, 새로 쓴 세이브는 다시 지워질 수 있는 제3자 저장소로 간다. 플레이어가 답했다면 Atelier 안이므로 대체 저장소를 쓰지 않는다. 거부되면 게임이 "불러오지 못했다"고 알리게 문서 예시를 바꿨다.

### 확인 방법

- 단위 테스트: 불러오기 실패 → hello·set·remove 모두 `load-failed`, 저장소의 진짜 세이브는 그대로 → 다시 hello하면 `storage-ready`에 진짜 세이브.
- 데모 모드 브라우저에서 허브의 `indexedDB.open`을 일부러 실패시켜 확인했다. 두 번 실패한 뒤 성공하면 게임이 다시 물어 진짜 세이브(`A-1`)를 받았다. 계속 실패하면 hello 1번과 재시도 3번 뒤 "불러오기 실패"를 띄우고 localStorage로 넘어가지 않았다. 실패 중 보낸 `storage-set`은 `load-failed`로 돌아왔고, 복구 뒤 hello에 진짜 세이브가 그대로 나왔다.

## 2026-11-10 · atelier-upload 스킬에 세이브 브리지 안내

### 업로드 절차에 "세이브 저장 확인" 단계를 넣고, 자세한 내용은 문서로 넘긴다

- **결정:** ZIP을 만들기 전 2단계로 넣는다. 세이브 사용처를 찾고, 브리지가 없으면 사용자 허락을 받아 바꾸고, 방법은 GitHub의 `docs/game-integration.md` 세이브 브리지 섹션을 읽고 따르게 한다. 스킬에는 놓치기 쉬운 요점(시작 전 `await`, `migrateKeys`에는 자기 키만)만 남겼다.
- **이유:** 코드를 스킬과 문서에 두 벌 두면 한쪽만 고쳐져 어긋난다. 업로드 직전이 빌드를 고칠 수 있는 마지막 시점이다. 세이브가 사라지는 문제로 들어온 요청에도 스킬이 걸리도록 description에 한 문장 더했다.
- **전용 스킬을 따로 만들지 않은 이유:** 세이브 브리지는 Atelier에 올릴 때만 필요하고, 스킬이 늘면 어느 쪽을 불러야 할지 흐려진다.
- **CLI는 다시 게시하지 않는다:** 스킬 파일은 npm 패키지(`files`)에 들어 있지 않다.

## 2026-11-10 · 게임 세이브 브리지

### 저장소는 IndexedDB, 키는 `[gameId, key]`

- **결정:** `src/lib/saveStore.ts`의 `SaveStore` 인터페이스(load/set/remove) 뒤에 IndexedDB 구현(`atelier-saves` DB, keyPath `["gameId","key"]`)을 둔다. IndexedDB가 없을 때만 localStorage(`atelier:save:{gameId}:{key}`)로 돌아간다.
- **이유:** 복합 키라 게임별로 범위 읽기 한 번에 불러오고, `atelier:theme` 같은 허브 키와 섞일 일이 없다. 수백 KB 세이브도 메인 스레드를 막지 않는다. Firestore 동기화는 같은 인터페이스의 다른 구현으로 붙이면 된다.

### 브리지는 메모리 사본을 두고 메시지를 순서대로 처리

- **결정:** `createSaveBridge(gameId, reply, store)`가 게임의 키-값을 메모리에 들고, `storage-set`을 받으면 사본을 바로 고친 뒤 저장소에 쓴다. 모든 메시지는 한 줄로 처리한다.
- **이유:** 게임이 저장하자마자 reload해서 `storage-hello`를 다시 보내도 새 값이 나간다. hello 직후 보낸 set이 불러오기보다 먼저 처리되는 일도 없다. 저장에 실패하면 사본을 되돌려 기기에 없는 값을 게임에 돌려주지 않는다.
- **용량 계산:** (키 길이 + 값 길이) × 2바이트, 게임당 5MB. 브라우저가 문자열을 UTF-16으로 세는 방식에 맞췄고, 같은 키를 덮어쓰면 이전 값은 빼고 센다.

### 리스너는 `useLayoutEffect`, 답장은 빌드 출처로만

- **결정:** `GameScreen`에서 `useSaveBridge`가 `useLayoutEffect`로 리스너를 붙이고, 브리지는 `gameId`마다 하나라 iframe이 다시 열려도 그대로 쓴다. `event.source`가 게임 iframe이고 `event.origin`이 플레이 URL의 출처일 때만 받고, 답장도 그 출처를 `targetOrigin`으로 보낸다.
- **이유:** 레이아웃 이펙트는 그리기 전에 실행되므로 iframe 문서가 먼저 메시지를 보낼 수 없다. 기존 전체화면 메시지는 불리언만 보내 `"*"`를 쓰지만, 세이브는 내용이 있으므로 iframe이 다른 출처로 이동했다면 보내지 않는다. 기존 전체화면 리스너는 건드리지 않았다.

### 게임 쪽 예시는 `createAtelierStorage()` 하나로

- **결정:** 문서와 테스트 빌드(`test-builds/save-bridge-test`)가 같은 클라이언트 코드를 쓴다. 1.5초 안에 ready가 없으면 localStorage로 돌아가고, `migrateKeys`에 적은 키만 한 번 옮긴 뒤 `atelier:migrated` 표시를 남긴다.
- **이유:** 지금까지 모든 게임이 같은 iframe 출처를 썼으므로 localStorage 전체를 옮기면 다른 게임의 세이브까지 가져온다. 옛 값을 지우지 않는 것은 옮기다 실패해도 원본이 남게 하기 위해서다.

### 확인 방법

- 단위 테스트(`saveBridge.test.ts`): 세션 사이 유지, reload 직후 최신 값, 같은 키 두 게임 분리, 메시지 속 gameId 무시, 허브 키와 분리, 한도·잘못된 값, 저장 실패 시 되돌림.
- 데모 모드 브라우저 확인: 테스트 빌드를 가리키는 임시 데모 항목 둘로 저장 → 게임 내 reload → 페이지 새로 열기 순서로 값이 남는 것, 같은 키를 쓴 두 게임이 분리되는 것, 허브 창과 다른 iframe에서 보낸 `storage-set`이 무시되는 것, 옛 localStorage 값 이전, 전체화면 메시지 동작을 확인했다. 임시 데모 항목은 되돌렸다. 실제 업로드 빌드(다른 출처 iframe)와 iPhone 홈 화면 앱에서는 아직 확인하지 않았다.

## 2026-11-10 · atelier.materialstone.dev 도메인 연결

### 경로(materialstone.dev/atelier) 대신 서브도메인(atelier.materialstone.dev)

- **이유:** 경로 방식이면 `materialstone.dev` 아래 모든 페이지가 한 origin이라 아틀리에의 Firebase 로그인 저장소와 localStorage를 함께 쓴다. 다른 페이지에 문제가 생기면 아틀리에 계정까지 영향을 받는다. 서브도메인은 origin이 분리되고, 나중에 아틀리에만 다른 호스팅으로 옮겨도 주소가 유지된다. 로그인이 없는 정적 페이지(개인정보처리방침 등)는 경로 방식도 괜찮다.
- **비용:** Vite base와 라우터 basename을 `/atelier/`에서 `/`로, manifest의 `id`·`start_url`·`scope`도 `/`로 바꿨다.

### 도메인 연결이 끝난 뒤에 이 변경을 병합한다

- **이유:** base가 `/`인 빌드를 `material-stone.github.io/atelier/`에서 열면 asset 경로가 깨진다. 그래서 DNS와 Pages custom domain이 먼저 동작한 뒤 병합한다. Firebase 승인 도메인·reCAPTCHA 허용 도메인·`PAGES_ORIGIN`·`SITE_URL`도 이때 함께 바꾼다.
- **옛 주소:** `material-stone-games/atelier`의 넘겨주는 페이지가 새 도메인으로 바로 보내도록 바꾼다. github.io를 거쳐 두 번 넘어가지 않게 하기 위해.
- **Cloudflare 프록시는 끈다:** 프록시를 켜면 GitHub Pages가 HTTPS 인증서를 발급하지 못한다.

## 2026-11-10 · atelier 저장소를 material-stone 조직으로 이전

### 주소를 새 조직 기준으로 바꾸고 옛 주소는 넘겨주는 페이지로 유지

- **결정:** 코드·문서의 사이트 주소를 `material-stone.github.io/atelier`로, 저장소 주소를 `github.com/material-stone/atelier`로 바꾼다. 비게 되는 `material-stone-games/atelier`에는 경로·쿼리·해시를 그대로 붙여 새 주소로 보내는 페이지만 둔다.
- **이유:** GitHub는 옛 Pages 주소를 새 주소로 연결해 주지 않는다. 유튜브 설명, 북마크, 게임 안 링크가 깨지지 않게 한다.
- **결정 기록 안의 옛 주소는 그대로 둔다:** 그 시점의 사실이기 때문이다.

### 순서: 새 도메인 허용 → 이전 → Functions 배포 → 옛 주소 페이지

- **이유:** Firebase Auth 승인 도메인과 App Check(reCAPTCHA) 허용 도메인에 새 도메인이 없으면 새 주소에서 로그인과 모든 callable이 막힌다. 그래서 이전 전에 추가한다. `PAGES_ORIGIN`은 게임 iframe의 `frame-ancestors`라서, 이전 직후 바꿔 배포해야 게임이 열린다.
- **사용자 영향:** 도메인이 바뀌면 브라우저에서는 다른 사이트라 모두 한 번 다시 로그인해야 하고, 브라우저에 저장한 설정이 초기화된다. 피할 방법이 없어 감수한다.

### CLI는 1.0.1로 다시 게시

- **이유:** npm 패키지의 저장소·문서 링크가 옛 주소를 가리킨다. 동작은 같다.

## 2026-11-10 · CLI 줄바꿈 고정과 배포 설정 정리

### tools/atelier-cli의 줄바꿈을 .gitattributes로 LF 고정

- **결정:** `tools/atelier-cli/** text eol=lf`. 저장소 전체가 아니라 이 폴더만 정한다.
- **이유:** Windows 체크아웃(`core.autocrlf=true`)에서는 `cli.mjs`가 CRLF가 되어, 그대로 npm에 올리면 macOS·Linux에서 `#!/usr/bin/env node
`를 찾지 못해 실행되지 않는다. 첫 게시 때는 손으로 LF로 바꿔 올렸다. 저장소 전체 규칙은 다른 파일의 줄바꿈까지 바꿔 큰 diff가 생기므로, 문제가 실제로 생기는 곳만 고정했다.

### functions/.env.example에 SITE_URL을 넣는다

- **이유:** 코드에 기본값이 있어도 `firebase deploy --non-interactive`는 `.env`에 값이 없는 파라미터를 거부했다. 첫 배포가 이 때문에 실패했다.

### npm 게시는 --auth-type=web과 보안 키로

- **이유:** npm은 게시에 2단계 인증을 요구하고, 새 설정에서는 보안 키만 고를 수 있어 `--otp` 코드가 없다. 브라우저 인증 링크에서 보안 키로 승인하는 방식이 동작했다. 이 절차와 "`tools/atelier-cli`에서 실행" 주의를 문서에 남겼다(한 번 저장소 루트에서 실행돼 거부된 적이 있다).

## 2026-11-10 · atelier-cli 이름과 하위 명령, npm 배포

### npm 패키지 이름은 @material-stone/atelier-cli

- **결정:** 명령 이름은 `atelier-cli`, 패키지 이름은 scope를 붙인 `@material-stone/atelier-cli`. scope 이름은 사용자가 정했다(사용자 판단 참고). GitHub 저장소는 아직 `material-stone-games`에 있어서 저장소·문서 링크는 지금 주소를 그대로 둔다.
- **이유:** `atelier-cli`라는 패키지 이름은 npm에서 이미 다른 사람이 쓰고 있다. scope 이름은 겹칠 일이 없고 누가 만든 패키지인지도 드러난다. 명령 이름은 `bin`으로 정해서 scope와 상관없이 `atelier-cli`로 쓸 수 있다.
- **대안:** `atelier-games-cli` 같은 다른 무scope 이름. 이름만 보고 출처를 알기 어렵고 나중에 또 겹칠 수 있어 뺐다.
- **라이선스:** 사용자가 정하지 않아서 `UNLICENSED`로 두었다. 설치와 사용은 되지만 재사용 허락은 하지 않는다는 뜻이다. 오픈소스로 열려면 MIT 등으로 바꾸면 된다.

### 하위 명령 구성

- **결정:** `login`, `logout`, `upload <zip>`, `status <gameId>`, `config`, `help`. 예전 `--init`은 `login --with-key`로 옮겼다. 키를 받는 일은 모두 `login` 아래에 둔다.
- **잘못 붙인 옵션은 오류로 막음:** `atelier-cli login --zip x`처럼 다른 명령의 옵션을 붙이면 조용히 무시하지 않고 알려 준다.
- **`--zip`도 계속 받음:** `upload build.zip`이 기본이지만 `upload --zip build.zip`도 된다.

### 설정 위치를 ~/.atelier-cli로, 도구 폴더 .env는 뺀다

- **결정:** 설정과 업로드 진행 상태를 `~/.atelier-cli/`에 둔다. 도구 폴더의 `.env` 읽기와 `.env.example`은 지웠다. 서버 주소는 설정이 없으면 코드의 기본값을 쓰고, 설정 파일에는 기본값과 다를 때만 적는다.
- **이유:** npm으로 설치하면 도구 폴더가 `node_modules` 안이라 `.env`를 둘 곳이 아니다. 예전 `~/.atelier-upload`는 아직 배포 전이라 실제로 쓰인 적이 없어 옮겨 읽지 않는다.
- **환경변수 이름은 유지:** `ATELIER_UPLOAD_URL`, `ATELIER_UPLOAD_KEY`는 업로드 API와 업로드 키를 가리키는 이름이라 그대로 둔다.

### 스킬 이름은 atelier-upload로 둔다

- **이유:** 스킬은 "게임을 올리는 절차"라서 이름이 하는 일과 맞고, 이미 전역 스킬 폴더에 같은 이름으로 설치되어 있다. 안의 명령만 `atelier-cli`로 바꿨다.

### npm에 올리는 파일은 cli.mjs와 README.md뿐

- **이유:** `files`로 제한해 스킬, 테스트 파일, 실수로 남은 설정이 패키지에 들어가지 않게 한다. 패키지를 누구나 설치할 수 있어도 키는 관리자 승인으로만 받으므로, 공개해도 업로드 권한이 퍼지지 않는다. 서버 주소는 이미 사이트 코드에 공개된 값이다.

## 2026-11-10 · 업로드 키 발급 서비스와 CLI 로그인

### Secret Manager 키를 없애고 Firestore에 해시로 저장한다

- **결정:** `UPLOAD_API_KEY` 시크릿을 지우고(아직 배포 전이라 옮길 데이터가 없었다), 키를 `apiKeys/{SHA-256 해시}`에 저장한다. 문서 id가 해시라서 요청마다 문서 하나만 읽으면 된다. 이 컬렉션에는 클라이언트 규칙이 없다.
- **이유:** 키 교체·폐기에 재배포가 필요 없어지고, 배포 순서도 상관없어진다. 키 목록과 마지막 사용 시각도 볼 수 있다. 키가 32바이트 난수라 무차별 대입이 불가능해서 bcrypt 같은 느린 해시가 필요 없다.
- **비용:** 업로드 요청마다 Firestore 읽기가 1회 늘어난다. 마지막 사용 시각은 10분에 한 번만 기록해 쓰기는 거의 늘지 않는다.
- **키 형식:** `atl_` + 32바이트 base64url. 접두어가 있으면 유출된 키를 로그나 시크릿 스캐너에서 알아보기 쉽다. 목록에는 앞 8글자만 보여 준다.

### CLI 로그인은 device code 방식

- **결정:** CLI가 코드와 폴링 토큰을 받는다. 관리자가 사이트의 `/cli-login`에서 Google로 로그인해 코드를 확인하고 승인하면, CLI가 폴링하다가 그때 키를 받는다.
- **이유:** 브라우저가 CLI의 로컬 서버(`127.0.0.1`)로 키를 넘기는 방식도 있었지만, Chrome이 공개 사이트에서 로컬 네트워크로 보내는 요청을 막거나 권한을 묻는 쪽으로 바뀌고 있어 불안정하다. 그 방식은 SSH로 접속한 원격 기기에서도 쓸 수 없다. device code 방식은 둘 다 문제없다.
- **키 원문을 저장하지 않음:** 승인할 때는 상태만 바꾸고, 키는 CLI가 받아 가는 트랜잭션 안에서 만들어 해시만 저장한다. 그래서 승인과 수령 사이에도 키 원문이 서버에 남지 않는다.
- **폴링 토큰:** 코드는 화면과 URL에 보이지만 폴링 토큰은 CLI만 갖고 있다. 그래서 링크나 화면을 본 다른 사람이 키를 받아 갈 수 없다.
- **피싱 대비:** 남이 시작한 로그인 링크를 관리자에게 보내 승인을 유도하는 공격이 이 방식의 대표적인 약점이다. 그래서 승인 화면에 요청한 기기 이름과 코드를 크게 보여 주고, 터미널의 코드와 같을 때만 승인하라고 적었다.
- **남용 방지:** 시작 경로는 인증 없이 열려 있다. 그래서 요청은 10분 뒤 만료되고, 새 요청이 올 때 만료된 것을 지우며, 진행 중인 요청은 20개로 제한한다. 함수 인스턴스도 1개다.
- **코드 모양:** 모음과 헷갈리는 글자(0/O, 1/I/L)를 뺀 8자리(`BX4K-9TQM`). 소리 내 읽기 쉽고 우연히 단어가 되지 않는다.

### 설정 창에 관리자 전용 "업로드 키" 탭

- **결정:** 지난 PR에서 만든 설정 창에 탭을 추가한다. CLI 로그인 안내, 직접 발급(한 번만 표시, 복사 버튼), 사용 중인 키 목록(이름, 발급 경로, 발급일, 마지막 사용), 폐기, 접힌 폐기 목록으로 구성했다.
- **이유:** 관리 기능은 업로드 룸에도 있지만, 키는 계정과 기기에 관한 설정이라 설정 창이 더 자연스럽다. 직접 발급은 CI처럼 브라우저로 로그인할 수 없는 곳을 위해 남겼다.
- **목록은 설정 창이 열릴 때만 불러온다:** 관리자가 아닌 방문자나 설정 창을 열지 않는 경우에는 callable을 호출하지 않는다.

### `atelier-upload logout`은 서버에서 폐기까지 한다

- **결정:** `DELETE /keys/self`로 지금 키를 폐기한 뒤 설정 파일에서 지운다. 서버에 닿지 못하면 로컬에서만 지우고, 설정 창에서 직접 폐기하라고 안내한다.
- **이유:** 로컬에서만 지우면 그 키는 계속 유효한 채로 목록에 남는다.

### 스킬: Claude가 로그인을 시작하고, 승인은 사용자가

- **결정:** 키가 없으면 Claude가 `atelier-upload login`을 백그라운드로 실행하고 코드를 사용자에게 전한다. 사용자가 브라우저에서 직접 승인한다. Claude가 브라우저를 조작해 대신 승인하지는 않는다.
- **이유:** 키가 대화에 한 번도 나오지 않는다. 승인 버튼을 Claude가 누르면 사람이 확인하는 단계가 의미를 잃는다.

### 검증 범위

- CLI의 로그인·로그아웃·거절·키 없음 흐름은 가짜 서버로 확인했다.
- 승인 페이지와 키 설정 화면은 서비스 호출을 가짜로 바꾼 컴포넌트 테스트 9개로 확인했다(비로그인, 비관리자, 승인, 거절, 만료, 코드 입력, 목록, 한 번만 표시, 폐기 확인).
- 로컬 미리보기는 Firebase 설정이 없어 비로그인 화면까지만 확인했다. 실제 Firebase에서 처음부터 끝까지는 배포 후에 확인해야 한다.

## 2026-11-10 · 업로드 API — 게임 정보 반영 시점, 전역 CLI·스킬

### 바꾼 게임 정보는 별도 컬렉션에 보관했다가 공개 순간에 반영

- **결정:** 공개 중인 게임을 업데이트하면 바꾼 정보(제목, 설명, 장르, 접근 등급, 초대 이메일)를 `pendingGameUpdates/{versionId}`에 둔다. `processBuildZip`이 빌드를 공개할 때 같은 `update`로 함께 반영하고, 실패·취소·다른 업로드로 대체되면 버린다. 이로써 "중단 처리"에서 남은 한계로 적었던 항목을 해결했다(사용자 지적).
- **이유:** `games/{id}` 문서는 공개로 읽히므로 초대 이메일을 그 안에 둘 수 없다. 버전별 문서로 두면 같은 게임에 업로드가 겹쳐도 어느 정보가 어느 빌드와 짝인지 헷갈리지 않는다. 규칙에 이 컬렉션을 넣지 않아서 클라이언트는 읽거나 쓸 수 없다.
- **순서:** 비공개로 바뀔 때는 초대 목록을 먼저 쓰고, 비공개에서 벗어날 때는 게임 문서를 바꾼 뒤 지운다. 기존에 정보를 직접 수정할 때와 같은 순서다.
- **범위:** 웹 업로드 룸도 같은 `prepareGameDraft`를 쓰므로 똑같이 바뀐다. 업로드가 끝나기 전에 정보가 먼저 바뀌는 문제는 웹에도 똑같이 있었기 때문에 따로 남겨 두지 않았다. 아직 공개되지 않은 게임(처리 중, 실패)은 누구에게도 보이지 않으므로 지금처럼 바로 반영한다.
- **알아둘 점:** 업데이트가 처리되는 동안 관리자 화면에서 정보를 직접 고치면, 빌드가 공개될 때 보관해 둔 값으로 덮어써진다.

### 전역 CLI는 `npm link`, 설정은 사용자 홈 폴더의 파일 하나

- **결정:** `tools/atelier-upload/package.json`의 `bin`으로 `atelier-upload` 명령을 만들고 `npm link`로 전역 설치한다. 키와 URL은 `atelier-upload --init`으로 `~/.atelier-upload/config`에 저장한다. 읽는 순서는 환경변수 > 사용자 설정 > 도구 폴더 `.env`다.
- **이유:** 링크라서 Atelier 저장소를 pull하면 모든 프로젝트에서 바로 새 버전을 쓴다. 키가 PC에 한 곳에만 있어서, 바꿀 때도 한 곳만 고치면 된다. 프로젝트마다 `.env`를 복사하면 키가 여기저기 흩어진다.
- **주의:** worktree에서 `npm link`를 하면 worktree가 지워질 때 링크가 깨진다. 그래서 원본 체크아웃에서 설치하도록 문서에 적었다. 검증할 때는 worktree에서 잠깐 링크했다가 해제했다.
- **`--config`:** 키를 가린 채 어디서 읽었는지 보여 준다. Claude가 키 원문을 보지 않고도 준비됐는지 확인할 수 있다.

### 스킬은 CLI를 감싸는 사용 설명서로 한정

- **결정:** 전역 스킬 `atelier-upload`에는 업로드 로직 없이 절차만 담는다: 준비 확인, ZIP 만들기, 새 게임과 업데이트 구분, 실패했을 때 대처. 원본은 저장소의 `tools/atelier-upload/skill/SKILL.md`에 두고 `~/.claude/skills/`에 복사한다.
- **이유:** 업로드 로직이 스킬에 있으면 Claude가 매번 코드를 다시 쓰게 되어 불안정하다. 원본을 저장소에 두면 변경 이력이 남는다. Windows에서 심볼릭 링크는 관리자 권한이나 개발자 모드가 필요해서 복사로 했다.
- **키 취급:** 스킬은 키를 대화로 받거나 명령줄 인자로 넘기지 말고, `--init`은 사용자가 직접 실행하게 한다. 키는 관리자 권한과 같아서 대화 기록이나 셸 기록에 남지 않게 했다.
- **ZIP 만들기:** 앞에서 "폴더를 ZIP으로 묶는 기능은 CLI에 넣지 않는다"고 정한 대신, 스킬에서 Windows 내장 `tar.exe -a`로 묶도록 했다. Git Bash의 `tar`는 GNU tar라서 ZIP을 만들지 못하므로 경로를 지정해 부른다. 이렇게 만든 ZIP은 항목이 `./`로 시작하지만 서버의 `safeArchivePath`가 이를 제거하는 것을 확인했다.

## 2026-11-10 · 업로드 API — 중단 처리

### Ctrl+C는 취소, 연결 실패는 이어 올리기

- **결정:** 사용자가 Ctrl+C를 누르면 업로드 세션을 끊고 서버 초안을 되돌린다. 재시도까지 실패했거나 프로세스가 죽은 경우에는 진행 상태를 남겨 두고, 같은 명령을 다시 실행하면 이어서 올린다. `--cancel`로 명시적으로 되돌릴 수 있다.
- **이유:** Ctrl+C는 "그만두겠다"는 뜻이 분명하니 흔적을 남기지 않는 게 맞다. 연결 실패는 사용자가 원한 중단이 아니라서, 250MiB를 처음부터 다시 올리게 하는 것보다 이어 올리는 게 낫다.
- **대안:** Ctrl+C도 이어 올리기용으로 남기는 방법이 있었지만, 그러면 '처리 중'으로 남은 게임을 사용자가 직접 치워야 해서 이번 작업의 목적과 맞지 않는다.

### 서버 취소는 "아직 처리 대기 중인 이번 버전"에만 작동한다

- **결정:** `DELETE /games/{id}/versions/{versionId}`는 그 버전이 아직 대기 중일 때만 되돌린다. 게임 문서는 이번 업로드로 처음 만들어졌을 때만 지운다. 이를 판단하려고 새 게임에 `createdByVersionId`를 기록하고, 공개되면 지운다.
- **이유:** 늦게 도착한 취소 요청이 이미 공개된 빌드나 그 사이 올라온 다른 업로드, 예전부터 있던 게임을 지우면 안 된다.
- **추가 안전장치:** CLI는 취소하기 전에 ZIP이 Storage에 다 올라갔는지 확인한다. 다 올라갔으면 이미 처리가 시작됐으므로 취소하지 않는다.

### 업데이트는 ZIP을 먼저, 표지를 나중에

- **결정:** 새 게임은 표지 → ZIP, 업데이트는 ZIP → 표지 순서로 올린다.
- **이유:** 업데이트 중에 멈추면 표지만 새것으로 바뀐 채 빌드는 예전 것인 상태가 생긴다. 표지는 같은 경로를 덮어쓰기 때문에 되돌릴 방법이 없다. 새 게임은 ZIP이 처리되는 순간 공개되므로 표지가 먼저 있어야 한다.
- **남은 한계:** 업데이트 때 함께 바꾼 제목·설명은 초안을 만들 때 바로 반영돼, 취소해도 되돌리지 않는다. 이전 값을 보관했다가 복원할 만큼의 문제는 아니라고 판단했다.

### 진행 상태는 사용자 홈 폴더에 저장

- **결정:** `~/.atelier-upload/state/<해시>.json`. 해시는 API URL, 요청 내용, 파일 경로·크기·수정 시각으로 만든다. 6일이 지나면 버린다.
- **이유:** 저장소 안에 두면 git에 섞일 수 있고, 나중에 CLI를 전역으로 쓰게 돼도 위치가 바뀌지 않는다. 파일이 바뀌었는데 이어 올리면 망가진 ZIP이 되므로, 수정 시각까지 포함해 같은 파일일 때만 이어 올린다. 업로드 세션 유효기간(7일)보다 조금 짧게 잡았다.

## 2026-11-10 · 업로드 API

### 파일은 함수를 거치지 않고 Cloud Storage로 직접 보낸다

- **결정:** API는 게임 문서만 갱신하고 Cloud Storage resumable upload 세션 URL을 돌려준다. CLI가 그 URL로 파일을 직접 PUT한다.
- **이유:** Cloud Functions 요청 본문은 32MB까지라 250MiB ZIP을 받을 수 없다. 함수를 통과한 바이트는 전송 요금도 붙는다. 웹 업로드도 이미 Storage로 직접 올리는 구조라 그대로 따랐다.
- **대안:** 서명 URL(v4 PUT)도 가능했지만 한 번에 올려야 해서 끊기면 처음부터 다시 해야 한다. resumable 세션은 8MiB씩 올리다 끊겨도 이어서 올릴 수 있고, URL 서명 권한도 필요 없다.

### 검사·압축 해제는 기존 processBuildZip을 그대로 쓴다

- **결정:** API로 올린 ZIP도 `incoming-builds/upload-api/{gameId}/{versionId}.zip`에 떨어져 같은 트리거가 처리한다. 초안을 만드는 코드는 `prepareGameDraft`로 빼서 웹 callable과 API가 함께 쓴다.
- **이유:** 경로 순회·용량·파일 수 검사, 이전 빌드 유지, 실패 시 롤백 같은 규칙을 두 군데서 따로 관리하면 언젠가 어긋난다.

### 인증은 Secret Manager에 둔 API 키 하나

- **결정:** `UPLOAD_API_KEY` 시크릿과 `Authorization: Bearer` 헤더로 인증한다. 키는 관리자 권한으로 취급한다.
- **이유:** 관리자가 한 명이고 목적이 자동화라서, Google 로그인 토큰을 갱신하거나 서비스 계정 JSON을 다루는 것보다 단순하다. App Check는 브라우저용이라 이 함수에는 걸지 않았다.
- **대안:** 로컬에서 `firebase-admin`과 gcloud 자격증명으로 직접 올리는 스크립트도 가능했지만, gcloud 로그인이 필요한 기기에서만 쓸 수 있고 요청한 "API"가 아니다.

### 기존 게임 업데이트 때 생략한 항목은 지금 값을 유지한다

- **결정:** `gameId`나 같은 제목으로 기존 게임을 지정하면, 요청에 없는 제목·설명·장르·접근 등급·초대 이메일은 기존 값을 채워 넣는다. 제목을 바꿀 때는 다른 게임과 겹치는지 확인한다.
- **이유:** 웹 업로드 룸은 폼 내용으로 메타데이터를 덮어써서, 빌드만 바꾸려다 설명이 지워지는 일이 있었다. 자동화에서는 "빌드만 교체"가 가장 흔한 작업이다.
- **결과:** 웹 업로드 룸의 덮어쓰기 동작은 바꾸지 않았다(요청 범위 밖).

### CLI는 의존성 없는 Node 스크립트

- **결정:** `tools/atelier-upload/upload.mjs`는 Node 18+ 내장 `fetch`만 쓴다. 설정은 환경변수나 같은 폴더의 `.env`(git 제외)에서 읽는다.
- **이유:** `npm install` 없이 어느 기기에서든, Claude가 Bash로 바로 실행할 수 있게.
- **안 한 것:** 폴더를 받아 ZIP으로 묶는 기능은 넣지 않았다. Node 내장 기능으로는 ZIP을 만들 수 없어 의존성이 생기고, Windows `Compress-Archive`는 버전에 따라 경로 구분자가 `\`로 들어가 서버 검사에 걸릴 수 있다.

### 새 게임은 표지 필수, 업데이트는 선택

- **결정:** 웹 업로드 룸과 같은 규칙. 업데이트에서 표지를 생략하면 기존 표지를 유지한다.
- **이유:** 홈 화면 카드에 표지가 없으면 깨져 보인다.

### 처리 완료까지 기다린다 (기본값)

- **결정:** CLI는 업로드 후 5초마다 상태를 확인해 공개·실패를 알려 준다. 최대 12분(`processBuildZip` 제한 9분 + 여유). `--no-wait`로 끌 수 있다.
- **이유:** 자동화에서는 "올렸다"보다 "공개됐다/실패했다(이유)"가 필요하다.
