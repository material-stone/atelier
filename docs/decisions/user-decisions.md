# 사용자 판단 기록

사용자가 정한 방향과 요구사항, 그 이유입니다. Claude의 설계 판단은 [claude-decisions.md](claude-decisions.md)에 있습니다.

## 2026-11-12 · 전체화면 버튼 항상 표시

### 전체화면 버튼을 숨기지 말고 비활성으로 표시한다

- **결정:** 플레이어 헤더의 전체화면 버튼이 로딩·잠금 중에는 사라졌다가 게임이 열리면 나타나는 것을 보고, 아이콘은 늘 두고 활성/비활성으로만 구분해 달라고 했다.
- **이유:** 버튼이 생겼다 없어지면 기능이 있다 없다 하는 것처럼 보이고 헤더가 흔들린다.

## 2026-11-11 · OAuth 데모 영상·자막 보관

### 바탕화면의 데모 영상과 자막을 프로젝트에 보관한다

- **결정:** 바탕화면에 있던 자막 입힌 데모 영상과 자막 파일을 프로젝트 안에 보관해 달라고 했다.
- **이유:** 검토 중 추가 자료 요청이나 재제출 때 다시 쓸 수 있게 한다.

## 2026-11-11 · 구독 확인 주 단위 유지와 로그인 직후 안내

### 구독자가 헤매지 않게 한다

- **결정:** 로그인과 구독 확인이 나뉘어 있어 구독자가 헤맬 수 있다고 지적했고, Claude가 추천한 조합(유효기간을 로테이션 주 끝까지 늘리기 + 로그인 직후 안내)을 승인했다.
- **이유:** 로그인 자체에 YouTube 권한을 붙이면 구독자가 아닌 사람까지 민감한 범위 동의 화면을 거치므로, 분리는 유지하고 확인 횟수와 찾는 수고를 줄인다.

## 2026-11-11 · YouTube 구독 확인 해제 버튼

### 구독 확인을 사용자가 직접 초기화한다

- **결정:** 한 번 확인하면 24시간 동안 "확인됨"으로 남아 OAuth 데모 영상을 다시 찍기 어렵다며, 확인을 초기화하는 버튼이 있으면 좋겠다고 했다.
- **이유:** 영상 녹화처럼 처음부터 다시 확인해야 할 때 Firestore 콘솔을 열지 않아도 되게 한다.

## 2026-11-11 · YouTube 구독 확인의 "확인되지 않은 앱" 경고

### 경고 화면을 없앤다

- **결정:** 일반 Gmail 계정으로 구독 확인을 하면 "Google에서 확인하지 않은 앱" 화면이 떠서 사용자가 거부감을 느끼므로 해결해 달라고 했다.

## 2026-11-11 · 단계 태그와 접근 등급 분리

### 공개 범위를 공개·데모(누구나) / 프로토타입(멤버) / 주간 로테이션(구독자)으로 나눈다

- **결정:** 공개와 데모는 모든 사용자, 프로토타입은 YouTube 채널 멤버십 회원, 프로토타입 중 주간 로테이션은 일반 구독자가 플레이한다.
- **이유:** 무료 → 구독 → 멤버십으로 단계마다 다음 단계로 넘어갈 이유를 만든다. 지금까지는 구독만 해도 프로토타입을 모두 할 수 있어 멤버십만의 혜택이 약했다.

### 단계 태그와 접근 등급을 따로 둔다

- **결정:** Claude가 제안한 분리(표시용 단계 + 권한용 접근 등급)에 사용자가 동의했다.
- **이유:** 공개와 데모는 접근 조건이 같아지고 라벨만 다르므로 한 값에 섞을 이유가 없다.

### 얼리 액세스는 프로토타입에 합친다

- **결정:** 기존 `member`(얼리 액세스) 게임은 프로토타입이 되고 로테이션 대상에도 들어간다.

### 로테이션은 매주 자동으로 30%, 지난주 게임은 빼고

- **결정:** 매주 프로토타입의 30%를 자동으로 무작위로 고르고, 지난주에 열린 게임은 다시 고르지 않는다.

### `login` 등급을 없앤다

- **결정:** 사용자가 "로그인해야 세이브 동기화를 할 수 있느냐"고 물었고, 지금 세이브는 기기에만 저장되어 로그인이 필요 없다는 답을 듣고 없애기로 했다.
- **이유:** 데모가 `public`이 되면 쓰는 게임이 없다. 나중에 기기 간 동기화를 붙여도 "동기화하려면 로그인"이지 플레이를 막을 일은 아니다.

### `subscriber`(구독자 전용) 등급도 없앤다

- **결정:** Claude가 선택지로 남겨 둔 구독자 전용 등급을 사용자가 쓰지 않겠다고 했다. 구독 확인은 주간 로테이션을 여는 데만 쓴다.

## 2026-11-11 · 플레이 세션 만료 자동 갱신

### 폰을 접었다 켜도 게임이 "세션 만료"로 멈추지 않게 한다

- **결정:** 사용자가 받은 피드백("세션 만료됨 표시가 남. 게임 다시 들어가도 만료되지 말아야함")을 고쳐 달라고 했다. 게임을 하다 폰을 접고 다시 켰을 때 만료 문구 대신 게임이 그대로 보여야 한다.
- **이유:** 플레이어가 잠깐 폰을 닫았을 뿐인데 게임 화면이 오류 문구로 바뀌고, 다시 하려면 직접 새로고침해야 했다.

## 2026-11-10 · 세이브 브리지 불러오기 실패 처리

### 불러오기 실패를 빈 세이브로 보내지 않는다

- **결정:** 사용자가 받은 피드백을 확인하고 고쳐 달라고 했다. 피드백 내용은 이렇다. 불러오기에 실패하면 `storage-ready` 대신 `atelier:storage-error`(`key: null`, `reason: "load-failed"`)를 보낸다. 다음 `storage-hello`에서 다시 불러온다. 불러오지 못한 동안 온 `storage-set`·`storage-remove`는 쓰지 않고 같은 오류로 돌려준다. 문서와 게임 쪽 예시도 이에 맞춘다.
- **이유:** IndexedDB가 잠깐 열리지 않았을 뿐인데 게임이 "세이브 없음"으로 보고 이어하기를 숨긴다. 그 상태에서 새 게임을 저장하면 기기에 남은 진짜 세이브를 덮어쓴다.

## 2026-11-10 · atelier-upload 스킬에 세이브 브리지 안내

### 다른 프로젝트 세션이 세이브 브리지를 스스로 적용하게 한다

- **결정:** Claude가 제안한 두 방법(전역 `atelier-upload` 스킬에 단락 추가 / 세이브 브리지 전용 스킬) 중 스킬에 추가하는 쪽을 사용자가 승인했다.
- **이유:** 게임 프로젝트 세션은 Atelier 저장소의 `docs/`를 보지 않으므로, 업로드할 때 항상 불러오는 스킬에서 안내해야 한다.

## 2026-11-10 · 게임 세이브 브리지

### 게임 세이브를 허브 저장소에 맡기는 브리지를 만든다

- **결정:** 사용자가 문제("양파로 빚 갚기"의 세이브가 PWA를 껐다 켜면 사라짐), 원인(게임 iframe이 제3자 컨텍스트라 저장소가 지워짐), 프로토콜(`atelier:storage-hello/ready/set/remove/error`)과 허브 요구사항을 정해 요청했다. 게임 구분은 허브가 아는 `gameId`로 하고, 보낸 창을 확인하고, 게임당 용량·키 길이 한도를 두고, `navigator.storage.persist()`를 요청한다.
- **범위:** 기기 단위 저장(IndexedDB 권장)까지. 로그인 사용자의 Firestore 동기화는 이번 범위가 아니며, 나중에 붙일 수 있게 저장 부분을 한 모듈로 분리한다.
- **이유:** 제3자 저장소는 게임 쪽에서 지킬 방법이 없고, 허브 페이지의 저장소는 제1자라 남는다. 모든 게임이 같은 출처를 써서 키가 겹치면 서로 덮어쓰는 문제도 함께 없앤다.

## 2026-11-10 · atelier.materialstone.dev 도메인 연결

### 자체 도메인 materialstone.dev를 쓰고, 아틀리에는 서브도메인으로

- **결정:** 사용자는 나중에 다른 웹페이지 그룹도 만들 수 있게 `materialstone.dev`를 쓰자고 했다(처음 제안은 `materialstone.dev/atelier`). Claude가 로그인이 있는 아틀리에는 서브도메인 `atelier.materialstone.dev`가 낫다고 추천했고, 사용자가 그대로 승인했다.
- **이유:** 여러 웹페이지를 한 도메인 아래 묶기 위해. 서브도메인을 택한 이유는 Claude 판단 참고.

- **이유:** 앞으로 쓸 조직으로 정리한다. 나머지(PokeDetective, 개인정보처리방침 페이지 둘)는 나중에 정한다.

### 배포에서 드러난 문제를 저장소에 반영한다

## 2026-11-10 · atelier-cli 이름과 하위 명령, npm 배포

### 도구 이름을 atelier-cli로 바꾸고 하위 명령으로 구성한다

- **결정:** `atelier-upload`를 `atelier-cli`로 바꾸고, `atelier-cli login`, `atelier-cli upload`처럼 하위 명령으로 쓴다.
- **이유:** 업로드만 하는 도구가 아니라 로그인 등 여러 일을 하는 Atelier 명령줄 도구이므로 이름과 구성을 그에 맞춘다.

### 외부에서도 설치할 수 있게 npm에 등록한다

- **결정:** 저장소 체크아웃 없이 `npm install -g`로 설치할 수 있게 npm 패키지로 낸다. 실제 배포(`npm publish`)는 사용자의 npm 계정으로 한다.
- **이유:** 다른 PC나 다른 환경에서도 저장소를 받지 않고 바로 쓰고 싶다.

### npm 패키지 이름은 @material-stone/atelier-cli

- **결정:** Claude가 처음 정한 `@material-stone-games/atelier-cli` 대신 `@material-stone/atelier-cli`로 한다. Claude가 추천한 대로 GitHub 조직 이름도 나중에 소문자-하이픈 `material-stone`으로 맞출 계획이고, 저장소 이전은 나중에 따로 한다.
- **이유:** 앞으로 쓸 조직 이름 `material-stone`에 맞춘다. 아직 npm에 올리기 전이라 지금 바꾸면 비용이 없다.

## 2026-11-10 · 업로드 키 발급 서비스와 CLI 로그인

### Atelier에서 업로드 키를 발급한다

- **결정:** 키를 Secret Manager에 직접 넣는 대신 Atelier 사이트에서 발급한다.
- **이유:** 배포 전에 키를 준비해야 하는 순서 문제가 불편했다. 사이트에서 발급하면 그런 절차가 필요 없다.

### CLI 로그인까지 만든다 (Google 로그인)

- **결정:** Claude가 "기본형(설정 창 발급·폐기)을 먼저 만들고 CLI 로그인은 나중에"를 추천했지만, 사용자는 처음부터 CLI 로그인까지 만들기로 했다. 로그인은 사이트의 Google 로그인을 쓴다.
- **이유:** 키를 복사해서 붙여 넣는 과정 없이 바로 쓰고 싶다.

## 2026-11-10 · 업로드 API — 게임 정보 반영 시점, 전역 CLI·스킬

### 업데이트 때 바꾼 제목·설명은 업로드가 다 끝난 뒤에 반영한다

- **결정:** 게임 정보를 업데이트 요청 시점에 바로 바꾸지 않고, 새 빌드 업로드와 처리가 끝난 뒤에 바꾼다.
- **이유:** 업로드가 중간에 멈추거나 실패했는데 제목·설명만 먼저 바뀌는 것은 맞지 않다. Claude가 처음에 "남은 한계"로 두었던 동작을 사용자가 바로잡았다.

### CLI는 전역 명령으로, 사용법은 전역 스킬로 만든다

- **결정:** Claude가 제안한 "전역 CLI + 전역 스킬" 방식을 승인했다.
- **이유:** 다른 프로젝트에서도 같은 API 키로 편하게 올리고 싶다.

## 2026-11-10 · 업로드 API — 중단 처리

### 업로드가 중간에 멈췄을 때의 처리를 추가한다

- **이유:** 업로드가 끊기거나 중단되면 게임이 '처리 중' 상태로 남는 점을 확인했고, 자동화 도구라면 정리까지 되어야 한다.

### 다른 프로젝트에서도 같은 API 키를 쓴다

- **결정:** 프로젝트마다 키를 따로 발급하지 않고 하나의 키를 함께 쓴다. 그래서 키를 여러 개 등록하는 기능은 만들지 않는다.
- **이유:** 여러 프로젝트에서 같은 방식으로 간단하게 올리고 싶다.

## 2026-11-10 · 업로드 API

### 웹 업로드 룸은 그대로 두고, 웹페이지를 거치지 않는 업로드 API를 추가한다

- **이유:** 지금은 Claude가 브라우저를 조작해 업로드 룸에서 올리는데, 20MB가 넘는 파일은 Claude가 브라우저로 직접 올려 주지 않는다. 자동화 도구로 더 편하고 빠르게 올리고 싶다.
- **유지할 것:** 웹페이지 업로드 방식은 없애지 않는다.

### 앞으로 기능 추가·수정 때마다 결정 기록을 남긴다

- **결정:** 누가 어떤 판단을 했는지와 이유를 문서로 남기고, 사용자 판단과 Claude 판단을 나눠서 볼 수 있게 한다.
- **이유:** 나중에 왜 이렇게 만들었는지 되짚을 수 있게 하기 위해.
